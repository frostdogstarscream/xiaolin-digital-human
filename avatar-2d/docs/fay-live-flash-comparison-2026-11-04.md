# 千问 / MiMo / DeepSeek：正式 Fay 问答对照

测试日期：2026-11-04。使用当前运行中的 Fay、OpenCode Go、百炼实时 TTS 和原有 LiveTalking WebRTC 展示；没有重启服务或创建新展示会话。

结论：在当前真实 Fay 上下文中，千问3.8 Flash 和 MiMo-V2.6-Flash 关闭思考后，仍需约3.6–4.9秒才收到模型首个正文。本轮没有显示出替换它们能明显缩短等待；同轮 DeepSeek 对照略快，但每款仅2次，不能作长期排名。

## 同轮分段观察

- 入口至 Fay 问答函数：约21–27ms。上次启动后首条问答的约1.045秒前置等待在本轮没有复现，不能当作每次必有的固定开销。
- 人设、上下文、历史和提示词准备：约3.3–5.1ms。
- 首个正文至首段入队：约0.7–85.2ms；本次回复均不足20字，以流结束 flush 为主。
- 五条实时合成样本的首块 PCM 等待：约0.530–0.777秒。
- 五条实时合成样本的首 PCM 至播放回调：约0.251–0.360秒。
- 所有正式样本均为 `route=direct`、`tool_count=0`，未调用大模型或独立意图判断模型，关联记忆检索仍跳过。

模型调用至首正文仍是最大的共同等待窗口。当前证据不足以将其继续归因于 SDK、网络、Go 路由排队或模型本身。下一步有价值的对照是固定完全相同的 Fay 消息输入，比较现有 LangChain 客户端与直接 HTTP 的时间，并记录 HTTP 发送、响应头和首正文边界。

## 参数、样本与缓存说明

Qwen 使用上一轮已通过的 `reasoning_effort=none`。MiMo 先进行1次直接接口兼容性检查：HTTP200、完整正文，未返回可见思考；之后正式使用同一 none 设置。DeepSeek沿用用户选定的关闭思考 + low。

顺序为 Qwen→MiMo→DeepSeek，再 DeepSeek→MiMo→Qwen。第二轮首次 DeepSeek 尝试命中语音缓存，旧观察器要求所有音频必须为实时PCM，故将该次文件播放拒绝为不合格样本并自动恢复配置。随后保留原报告快照，修正测试观察器区分实时与文件音频，补齐后三次。业务缓存未清理，服务实现未改动。总计1次MiMo兼容检查、7次正式问答尝试，其中6次保留为完整对照样本，另1次缓存尝试保留在原始日志和中断报告记录中。

历史不清空、不回写旧数据库快照，随正式测试正常追加；每次取30条记录并整理为20条消息，提示词总长度1655–1728字符。因此这是同一正式配置下的短样本对照，不是冻结完全相同消息的严格基准；未测物理麦克风和外放听感。
